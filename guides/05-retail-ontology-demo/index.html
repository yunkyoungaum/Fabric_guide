Retail Ontology Agent 데모 — 가이드 & 설명

4개의 서로 다른 물리 데이터 계층(Lakehouse 관리형 Delta · ADLS 단축 · SharePoint Excel · Eventhouse)을 하나의 온톨로지로 묶고, 그 위에서 Data Agent가 자연어로 비즈니스 질문에 답하는 옴니채널 리테일 데모입니다. 이 문서는 데모의 구조·데이터·시나리오·운영을 설명하고, 그대로 재현·발표하는 방법을 안내합니다.

한 줄 요약 — 생성 데이터의 프로모션(PR9999, Seoul Audio Summer Surge)에서 높은 장바구니 이벤트 수·낮은 구매 이벤트 수·낮은 재고가 함께 관찰됩니다. Data Agent가 온톨로지 관계로 근거를 연결해 재고 제약 가설을 설명하는 데모이지, 재고 부족의 인과 효과를 입증하는 분석은 아닙니다.

1. 데모가 보여주는 것

  • 비즈니스 질문: 서울 오디오 여름 프로모션은 왜 고객 관심이 폭발했는데 매출은 저조했나?
  • 핵심 메시지: 온톨로지는 테이블·컬럼을 비즈니스 의미(엔터티·관계)로 바꾸고, Data Agent는 이름 매칭이 아니라 관계 그래프를 순회해 답을 만든다.
  • 주요 신호: PR9999에 귀속된 AddToCart 1,729건 vs Purchase 36건 → 이벤트 수 비율 2.08%(36÷1,729). 고유 고객·세션 기준 전환율은 아닙니다. 캠페인 기간 해당 매장·상품의 평균 재고는 1개로 보고되었습니다.
  • 액션 제안: 재고 확보 전 캠페인 예산 재배분을 검토하고, 개인화 동의를 가진 고가치 고객을 재접촉 후보로 선별합니다. 동의 플래그만으로 연락의 적법성이 보장되지는 않으며 채널별 동의·철회·정책을 별도 확인해야 합니다.

4.2 ADLS 단축 (복사 없는 외부 접근)

  • ADLS 경로: abfss://raw@ykexternaldatalake.dfs.core.windows.net/retail-ontology-demo/customer_profiles
  • OneLake 단축: RetailOperationsLH/Tables/customer_profiles

데모 기록은 customer_profiles를 외부 ADLS Delta에 대한 단축으로 설명합니다. 아래 Unity Catalog 화면은 관리형 Delta 테이블의 예시이며, 이 화면만으로 해당 ADLS 경로와 같은 데이터이거나 UC 관리형 테이블을 직접 읽는다고 검증할 수는 없습니다.

중요한 지원 범위 차이 — 현재 온톨로지 바인딩 문서는 관리형 Lakehouse 테이블만 지원하고 외부 위치의 테이블은 지원하지 않는다고 명시합니다. 따라서 이 데모의 Customer → customer_profiles 단축 바인딩은 보고된 구성이지 일반 지원 보장이 아닙니다. 재현 시 관리형 Delta로 적재하고 바인딩을 변경하는 경로를 검토하세요(복사·갱신 필요). OneLake security 또는 Delta column mapping이 활성화된 소스에도 제한이 있으므로, 동작을 위해 보안 기능을 임의로 해제하지 말고 승인된 별도 데모 데이터를 사용합니다.

6. Data Agent — RetailInsightAgent

6.1 그라운딩 지침(핵심)

에이전트는 7개 엔터티를 모두 선택하고, 다음과 같은 근거 기반 분석 지침으로 온톨로지 관계를 순회합니다.

  • 이름 매칭이 아니라 온톨로지 관계를 순회해서 답한다.
  • 행동=CustomerEvent, 재고=InventorySnapshot, 매출=Order, 캠페인=Promotion으로 매핑.
  • 데모에서 빈 결과가 보고된 3개 이상 엔터티 쿼리·NOT EXISTS/anti-join 패턴을 피하도록 지시합니다. Fabric 전체의 엔터티 수 제한이나 모든 anti-join 실패를 뜻하지는 않습니다.
  • 대신 분해(decompose): 엔터티별 단순 쿼리로 ID 목록을 얻고, 교집합·차집합을 직접 계산한다.
  • 가장 선택적인(작은) 엔터티부터 시작해 ID 목록을 큰 엔터티로 가져간다(잘림 위험 감소). 차집합 계산 전에는 양쪽 목록의 완전성을 확인해야 합니다.
  • count가 0보다 큰지 확인하기 전에 나눗셈하지 않는다.

데모 용어 정의 — 구매 의도=AddToCart, 구매 이벤트=Purchase, 고가치 고객=Segment 'High Value', 재접촉 후보=ConsentForPersonalization true, 재고 위험=OnHandQuantity ≤ ReorderPoint입니다. 지침은 모델 행동을 유도할 뿐, 접근 통제나 동의 정책을 강제하지 않습니다.

7. 데모 시나리오 (10개 질문 예시)

아래 수치는 제공된 데모 기록의 기대 결과이며 이번 검토에서 다시 실행하지 않았습니다. 이벤트 집계의 PromotionID·시간 범위·매장·상품 필터를 확인하세요. PR9999 귀속 이벤트와 캠페인 기간 재고는 서로 다른 집계 범위일 수 있습니다.

  • Which high-value customers showed purchase intent for P0001 but did not purchase, and may be contacted under their personalization consent? → 데모 보고 결과는 33명 중 약 32명 (C000006, C000021, C000037, …). 고가치·동의 고객을 먼저 좁힌 뒤 동일 기간의 AddToCart/Purchase 고객 집합을 비교합니다. 잘린 목록이나 근사값을 실제 연락 명단으로 사용하지 말고 원본 데이터와 최신 동의 상태를 검증합니다.

8. MCP로 외부 노출

Fabric은 Ontology MCP와 Data Agent MCP를 제공합니다. 아래에서는 공식 문서의 지원 범위와 사용자가 제공한 데모 호출 기록을 구분합니다. 이번 검토에서 엔드포인트를 호출하지 않았으며, 관찰된 응답·오류·시간이 모든 환경에서 재현된다고 보장하지 않습니다.

8.2 인증

Entra ID 인증이 필요하며 익명 공개가 아닙니다. 호출자에게 해당 항목과 필요한 원본 데이터의 유효 읽기 권한이 있어야 합니다. 에이전트 공유만으로 원본 접근이 부여되지는 않습니다(권한 문서). 아래는 로그인 후 사용하는 Bash/Azure CLI 예시입니다. MCP의 Fabric 토큰 scope는 https://api.fabric.microsoft.com/.default이며 토큰을 코드·로그·Git에 저장하지 않습니다.

TOKEN=$(az account get-access-token \
  --resource https://api.fabric.microsoft.com \
  --query accessToken -o tsv)

Data Agent MCP 문서는 사용자 및 서비스 주체 토큰을 명시적으로 지원합니다. 이는 테넌트의 Service principals can use Fabric APIs 스위치만으로 추론한 지원이 아닙니다. SPN 안내의 워크스페이스·소스 권한 및 제한(KQL 연결 에이전트와 managed identity 미지원)을 확인하세요. 해당 안내의 토큰 리소스 표기와 MCP 문서가 다르므로 MCP에는 위의 엔드포인트별 scope를 따릅니다. 직접 Ontology MCP의 SPN 지원은 확인한 문서에 명시되지 않아 별도 검증이 필요합니다. ADLS 단축의 Workspace Identity는 에이전트 호출 인증과 다른 계층입니다.

8.3 호출 방법

MCP는 JSON-RPC 2.0 / Streamable HTTP를 사용합니다. 먼저 initialize 협상과 notifications/initialized를 완료하고, 협상된 프로토콜 버전 및 서버가 발급한 세션 ID가 있으면 후속 요청에 전달해야 합니다. 공식 문서의 MCP SDK 예시가 이 흐름을 처리합니다. 아래 Bash 조각은 이미 초기화된 세션의 tools/list 메시지 예시이며 독립 실행 가능한 전체 클라이언트가 아닙니다. URL은 §8.1에서 선택하고 필요한 세션 헤더를 추가합니다.

# After MCP initialization; include negotiated protocol/session headers as applicable
curl -X POST "$URL" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

Ontology MCP 도구 2개 (인수는 데모 기록)

공식 Copilot Studio 연결 문서는 아래 두 도구 이름을 확인합니다. 인수와 반환 구조는 반드시 연결한 서버의 tools/list 스키마로 확인하세요.

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{
  "name":"list_ontology_entity_types",
  "arguments":{"includeProperties":true}}}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{
  "name":"search_ontology",
  "arguments":{"naturalLanguageQuery":"...","naturalLanguageResponse":true}}}

데모 기록에서 search_ontology는 structuredContent.raw에 집계 테이블을 반환했습니다. 아래는 생략된 응답 예시로, ...를 포함하므로 완전한 JSON은 아닙니다. 모든 호출의 반환 형식을 보장하지 않습니다.

{"Fields": ["promotion_id", "event_type", "event_count"],
 "Value": [["PR9999", "AddToCart", 1729], ["PR9999", "Purchase", 36], ...]}

Data Agent MCP가 주는 도구 1개

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{
  "name":"DataAgent_RetailInsightAgent",
  "arguments":{"userQuestion":"How many stores are there?"}}}

DataAgent_RetailInsightAgent와 userQuestion은 데모 기록의 예시입니다. 공식 문서는 이름·인수를 하드코딩하지 않고 tools/list의 name과 inputSchema로 검색하도록 안내합니다. 표시 이름 변경 시 도구 이름이 반드시 바뀐다고 가정하지 말고 재확인합니다.

8.4 MCP 클라이언트 등록

아래는 VS Code의 .vscode/mcp.json 형식이며 공식 Ontology URL을 사용합니다. 다른 클라이언트는 Streamable HTTP 및 Fabric 토큰 헤더 지원과 자체 설정 형식을 확인해야 합니다. 토큰 입력은 마스킹되지만 만료 후 갱신은 별도 필요합니다. Data Agent MCP는 dynamic client registration을 지원하지 않으므로 자동 OAuth 등록을 전제로 하지 마세요.

{
  "servers": {
    "fabric-ontology": {
      "type": "http",
      "url": "https://api.fabric.microsoft.com/v1/mcp/dataPlane/workspaces/8653f3c5-60af-4976-9aad-13f7c26b9d93/items/f7eecc18-db38-46f4-8815-90f5bb3deb21/ontologyEndpoint",
      "headers": { "Authorization": "Bearer ${input:fabricToken}" }
    }
  },
  "inputs": [
    { "id": "fabricToken", "type": "promptString", "description": "Fabric access token", "password": true }
  ]
}

클라이언트 타임아웃을 검토하세요. 17초(Ontology)·31초(Data Agent)는 제공된 개별 데모 관찰값이지 SLA나 동일 조건 벤치마크가 아닙니다. 첫 호출·질문·부하에 따라 달라질 수 있습니다. 공식 Data Agent MCP는 장기 요청에 tasks 확장도 설명하지만, 클라이언트의 지원 여부를 확인해야 합니다.

8.5 사전 조건

공식 문서 기준 유료 F2 이상 또는 Fabric이 활성화된 P1 이상 용량, 필요한 테넌트 기능과 권한이 필요합니다. Ontology item 설정 및 Data Agent의 AI 처리·저장 지역 설정도 조직 정책에 따라 확인합니다. F16/Korea Central이라는 데모 기록만으로 모든 기능의 가용성을 보장하지 않습니다.

8.8 주의사항

  • 둘 다 Preview입니다. 프로덕션 아키텍처 제안 시 명시해야 합니다.
  • 응답이 Fabric 규정 준수 경계·리전 밖으로 나갈 수 있습니다. MCP 클라이언트가 어디서 실행되고 데이터를 어떻게 저장하는지는 Fabric이 통제하지 못합니다. 거버넌스 검토 항목입니다.
  • 두 MCP 경로의 resources/list에서 -32601 Feature is not enabled가 보고되었습니다. 해당 데모 세션의 관찰이지 모든 버전의 기능 부재를 증명하지 않습니다. 초기화 응답의 capabilities와 도구 스키마를 확인하세요.
  • 공개 범위 검토: 실제 workspace/item ID, 스토리지 계정·컨테이너 경로, SharePoint 사이트·폴더 이름은 인프라 식별 정보입니다. 기존 데모 ID는 유지했으며 게시 여부는 소유자가 결정해야 합니다. 이 HTML 텍스트 검토에서 실제 토큰·암호·SAS는 발견하지 않았지만 이미지 검토는 별도입니다.

상세 요청 예시와 실측치는 리포지토리 docs/data-agent-operations.md에 정리되어 있습니다.

9. 알려진 한계 & 문제 해결

  • 복잡한 그래프 질의의 빈 결과(데모 관찰) → Part 3·4처럼 분해하고 바인딩·권한·필터를 확인합니다. 자연어 한 문장이 곧 하나의 그래프 쿼리는 아닙니다.

Retail Ontology Agent Demo — Guide & Explainer

An omnichannel retail demo that unifies four different physical data layers (Lakehouse managed Delta · ADLS shortcut · SharePoint Excel · Eventhouse) into a single ontology, on top of which a Data Agent answers business questions in natural language. This document explains the demo's architecture, data, scenario, and operations, and shows how to reproduce and present it.

In one line — the generated promotion data (PR9999, Seoul Audio Summer Surge) shows many cart events, few purchase events, and low stock together. The Data Agent connects evidence through ontology relationships to explain an inventory-constraint hypothesis, not to prove a causal effect of inventory scarcity.

1. What the Demo Shows

  • Business question: Why did the Seoul audio summer promotion draw huge customer interest yet produce weak sales?
  • Core message: an ontology turns tables/columns into business meaning (entities and relationships), and the Data Agent answers by traversing the relationship graph rather than matching names.
  • The key signal: 1,729 AddToCart vs. 36 Purchase events attributed to PR9999 → an event-count ratio of 2.08% (36÷1,729), not a unique-customer or session conversion rate. Reported average stock for that store/product during the campaign was 1 unit.
  • Proposed action: consider reallocating campaign budget until stock recovers and shortlist high-value customers with personalization consent for re-contact. That flag alone does not establish lawful contact; separately check channel consent, withdrawals, and policy.

6. Data Agent — RetailInsightAgent

6.1 Grounding instructions (key)

The agent selects all 7 entities and traverses ontology relationships under grounded analysis instructions:

  • Answer by traversing ontology relationships, not by matching names.
  • Map behavior=CustomerEvent, stock=InventorySnapshot, sales=Order, campaign=Promotion.
  • Instruct the agent to avoid 3+ entity queries and NOT EXISTS / anti-join patterns that reportedly returned empty results in this demo. This is not a Fabric-wide entity-count limit or a claim that every anti-join fails.
  • Instead decompose: one simple per-entity query for ID lists, then intersect/subtract yourself.
  • Begin with the smallest, most selective entity and carry its ID list into the larger one (reduces truncation risk). Verify both lists are complete before computing a set difference.
  • Never divide by a count before confirming it is greater than zero.

Demo terminology: purchase intent = AddToCart, purchase event = Purchase, high-value customer = Segment 'High Value', re-contact candidate = ConsentForPersonalization true, inventory risk = OnHandQuantity ≤ ReorderPoint. Instructions guide model behavior; they do not enforce access control or consent policy.

9. Known Limits & Troubleshooting

  • Empty results from complex graph queries (demo observation) → decompose as in Part 3/4 and check bindings, permissions, and filters. One natural-language sentence need not produce just one graph query.
  • Large identifier lists risk truncation → do not infer set differences or non-purchases from incomplete sets. Counts are not automatically trustworthy either: cross-check generated queries, filters, and source aggregates.
  • Rows in Instances do not prove the whole graph is current. The claim that it directly reads source bindings was not verified. Check graph refresh status against known source aggregates and relationships.
  • The Graph Model is not ready → opening/saving in the portal was a reported demo recovery step. Officially, after upstream changes, check the associated Graph item's Schedule → Refresh now or refresh schedule. Full refresh consumes capacity; follow official troubleshooting for binding, permission, or column-mapping issues.
  • An agent missing from the portal → first check workspace, permissions, item type, list filters, and service health. Deleting and recreating is not the default recovery procedure: it can break IDs, links, sharing, and publishing integrations. Only if necessary, back up definitions/settings and obtain owner approval before deploying and validating a separate item. This guide preserves existing demo IDs.
